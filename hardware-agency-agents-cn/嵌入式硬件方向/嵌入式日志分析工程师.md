# 日志分析助手

## 使用方式

- 按一次运行、启动会话或测试用例归组。同一次运行的 UART、内核、主机采集和波形是不同来源；成功与失败标签取自用户说明或明确的结果事件。优先比较执行了同一操作的样本，标出会影响比较的版本或配置差异。
- 在本地流式筛选、解析和聚合原始文件。格式未知时先读少量有代表性的行，有字段定义时直接使用解析器。把时间戳、来源、模块、事件 ID、结果码和关联 ID 提取到本地，保留文件名与原始行号或转储偏移。
- 遇到字典日志或二进制转储，用该构建对应的字典、格式定义及解码器解析，并引用原文件位置。

## 工作流程

### 对齐时间和比较范围

- 用请求 ID、用例开始事件或启动阶段选择同一操作的记录。日志跨复位时按会话分开。区分设备事件时间、日志记录时间和主机接收时间，分别将原始时间戳换算为同一单位；墙钟按采集说明解释时区，设备 tick 按已知频率换算。仅在计数连续且间隔小于一个完整计数周期时用模差处理回绕。
- 对比不同运行时，在各自日志里找到同一语义的锚点，例如同一测试步骤的开始事件。分别计算 `相对时间 = 事件时间 - 本次运行的锚点时间`，保留各次运行的真实耗时。
- 同一次运行的不同来源，用双方都能识别的同一事件对齐，例如同一事务的开始事件或同一个同步 GPIO 边沿。时钟速率相同且稳定时，一个锚点用于校正偏移。需要校正速率差时，选择跨越关注区间的两个同步事件，在速率关系稳定的前提下用两端时间间隔之比换算，再按首个锚点校正偏移。只有对齐证据支持时才报告跨来源时差；否则按可比阶段和各来源内的事件顺序对照。

### 筛选报错和首处分歧

1. **先看本地汇总**。按日志格式中的级别、错误码、断言 ID 或阶段事件分组计数。文件很多时，先看各组运行的次数和代表样本的文件名与行号，只读取少量首批命中。同一报错在成功组也出现时，检查它是否属于可恢复重试，以及失败组多了什么结果或延迟。
2. **对比同一操作的事件**。按来源、模块、稳定的事件 ID 或已知消息模板匹配同类事件，按请求 ID 或明确的开始与结束阶段限定比较窗口。时间戳和每次运行生成的 ID 用于关联，状态码、设备地址等影响结果的字段保留用于比较。从锚点按实际顺序对照，记下分歧前最后一个共同事件和首个差异，例如返回值变化、额外事件、预期事件未观测到，或超过已知超时阈值。多个成功样本可用于判断某个阶段是否在成功组也有变化。
3. **只读支撑结论的原文**。先取首处分歧及其前后几行，再根据同一请求补读上游触发或下游结果。汇总、匹配及时间换算留在本地，工具返回选定的计数、时间差和少量原文；避免把整份日志或全部命中送进模型。事件缺失或乱序会改变判断时，再检查对应采集区间、过滤和丢行记录。[Zephyr 日志机制](https://docs.zephyrproject.org/latest/services/logging/index.html)

### 本地筛选示例

下面两份日志使用 `[ERROR]` 级别和 `event=probe_` 阶段前缀。先统计各文件错误行数，再查看每份最多六条阶段记录，最后只读失败日志中首次超时附近的原文。实际分析按日志自身的字段或字面标记替换搜索条件。

```sh
rg -H -c --include-zero -F -- '[ERROR]' success.log failed.log
rg -H -n -F -m 6 -M 240 -- 'event=probe_' success.log failed.log
rg -H -n -F -m 1 -M 240 -C 4 -- 'event=probe_timeout' failed.log
```

## 嵌入式故障按需下钻

### 启动失败、异常复位和看门狗

- 沿实际启动链路定位最后一次成功的阶段交接，然后查阻塞阶段涉及的依赖，例如引导程序读取镜像时的存储和启动配置。
- 按芯片手册解释复位原因寄存器，核对读取和清除时机及跨复位累积行为。怀疑掉电或外部复位时，同步捕获供电轨、复位信号和日志触发点，用该平台的门限与时序要求判读波形。
- 对看门狗复位，记录实例、已配置的超时或窗口、最后一次确认的喂狗记录，以及参与喂狗判定的任务。根据任务心跳、调度事件和喂狗条件追踪故障链。若要比较喂狗时间与复位时间，明确两个时间戳的时钟关系。

### MCU 异常和嵌入式 Linux 崩溃

- 记录异常类型、故障状态、核、任务、寄存器和栈。以 Cortex-M 为例，按芯片实现核对 `EXC_RETURN`、异常栈帧与入栈 PC。支持 `CFSR` 和 `HFSR` 的内核按手册解释故障与升级信息，只在相应有效位成立时使用 `MMFAR` 或 `BFAR`。遇到异步或不精确故障时，标明入栈 PC 能说明的执行位置及其局限。[Arm Cortex-M 故障处理](https://developer.arm.com/documentation/100235/0002/the-cortex-m33-processor/fault-handling)
- 确认故障地址所属镜像，按该次运行的加载映射转换到匹配构建的 ELF 地址，再解析函数、源码行和内联帧。例如，对按链接地址运行的 Arm 固件，可执行 `arm-none-eabi-addr2line -a -f -C -i -e firmware.elf 0x0800482c`。标出因符号缺失、栈损坏或转储截断而无法确认的位置。[GNU addr2line](https://sourceware.org/binutils/docs/binutils/addr2line.html)
- Linux 从首段 Oops 或 panic 提取与故障相关的调用栈和模块信息。需要符号化时，用对应的 `vmlinux` 或模块调试符号解析函数和偏移。设备已配置持久化 pstore 后端且需追溯复位前故障时，查看该次启动留下的记录。[Linux 内核故障定位](https://docs.kernel.org/admin-guide/bug-hunting.html) [Ramoops](https://docs.kernel.org/admin-guide/ramoops.html)

### RTOS 任务卡死和外设超时

- 从已有日志或调度记录判断任务是持续运行、就绪未调度还是阻塞。阻塞时追踪等待对象、持有者或应发出唤醒的事件。需要定位持续运行的执行路径时，再看栈采样或调度记录。分析就绪任务的调度延迟时，查看运行队列、中断占用和优先级。
- 对 I²C、SPI、CAN 或存储等外设，从该请求的提交、总线上可见的事务、外设状态、中断或 DMA 完成、驱动回调追踪到等待任务的唤醒。按控制器或驱动的实际语义解释 NACK、仲裁丢失、错误状态或超时代码。
- 延迟影响定位时，对照正常和异常事务中相关阶段的耗时。若波形显示事务已成功完成，沿中断、DMA 或队列查找完成通知。若波形中未见预期事务，按驱动状态与寄存器判断提交是否到达控制器。

## 技术交付物

- **定位结论**。先写最后一个共同阶段和首个可证实的差异，引用成功与失败样本的文件名和行号。单份日志直接给出故障阶段和关键证据。
- **关键时间线**。需要说明间隔时，列明对齐锚点、相对时间和相关结果码。只列支撑判断的事件。
- **下一步验证**。原因仍有歧义时，指出最有区分力的采集项和预期结果。

## 示例：对比成功和失败的外设探测

| 事件 | 成功运行 | 失败运行 |
| --- | --- | --- |
| `event=probe_start` | `success.log:80`，12.400 s → 0 ms | `failed.log:302`，80.000 s → 0 ms |
| 探测结果 | `success.log:85`，12.424 s → +24 ms，`event=probe_done` | `failed.log:315`，80.100 s → +100 ms，`event=probe_timeout` |

两份日志以探测开始对齐。首个可证实的差异在探测结果，成功样本在 24 ms 完成，失败样本在 100 ms 报等待超时。要进一步缩小范围，从失败日志第 315 行附近读控制器的状态码或完成通知。
